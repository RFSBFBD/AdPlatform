# Typed conversion sources and lead optimization

Definitions belong to one owned connected ad account. `GET/POST /api/v1/ad-accounts/{id}/conversion-definitions` reads/declares them. POST requires manage-accounts or Owner/Admin. Required explicit semantics: external_key, name, kind (lead/qualified_lead/purchase/install/other), counting_method (events/fractional_attributed), attribution_model, click_window_days, view_window_days, source_system. The key is unique per account; existing definitions cannot be silently edited or relabeled. A changed definition gets a new key. These are user-declared, not API verified.

`POST /api/v1/ad-accounts/{id}/conversion-definitions/{definition}/daily-import` accepts one entity_level and1-1000 aggregate rows. Each row requires entity_id, date, count, currency, timezone, source_reference, retrieved_at. Entity must belong to the same account/provider through its full parent chain. Dates must be completed days. Currency/timezone match the account exactly, timezone must be known, retrieval must be after the observation day closes in account-local time and cannot be future. Counts allow at most4decimal places, matching storage without silent rounding. Events counts are integral. Fractional attributed counts require explicit counting semantics. No arbitrary extra row fields. Opaque source_reference uses letters/digits/underscores/dots/colons/hyphens, not a callback URL.

The complete batch validates before a transaction writes. Exact definition/entity-level/entity/day is replaced, not incremented: retries are idempotent, a corrected import restates that same day. This is aggregate-key upsert, NOT deduplication of people/events across sources. Import is a local data change, never a campaign change. No email, phone, customer identifier or free customer payload is required or accepted as a field. Never paste secrets or personal data into names/source keys. Definitions/source labels remain user-supplied metadata, not trusted instructions.

MAXIMIZE_LEADS requires conversion_definition_id of kind lead. It narrows to that explicit owned account, rather than silently pooling incompatible definitions across accounts. Every selected spend entity/day needs a typed count, and every typed entity/day needs matching spend. Thirty complete days and all existing fit/quality/currency/timezone/parent-chain gates apply. Generic PerformanceMetric.conversions and conversion_value are never relabeled, overwritten or used as the lead response. Objective is reported/imported lead counts, not qualified leads, unique customers, sales or profit. Existing continuous and explicit discrete menu solvers work on that typed response; discrete finite-menu limits still apply. Definition semantics, exact typed rows and fitted curves are archived with the optimization run. Base replay uses archived curves and does not fetch current lead records. No cross-source identity resolution, automatic CRM connector, event-level conversion ingestion, purchase value import or provider-specific lead metric mapping is implemented by this feature.

UI includes opt-in empty JSON source forms and an explicit lead definition selector by ID. Nothing uploads until the user submits; no real customer records are preloaded. Read endpoints are owner-scoped, write permission checked separately. This does not make historical imports provider-verified or prove their semantic truth.

MAXIMIZE_QUALIFIED_LEADS is a separate explicit objective requiring definition kind qualified_lead. A plain lead definition, generic conversions or missing definition cannot substitute. Uses response_metric typed_qualified_leads, the exact same scoped completed-day import/fit gates, continuous or explicit discrete solver, sensitivity, source archive and replay. This optimizes user-declared qualified-lead aggregate counts, not independently verified lead quality, unique customers or sales. It adds no CRM event ingestion, personal identifiers or funnel relationship between lead and qualified-lead definitions.

A separate minimal immutable event ledger now exists, see FIRST_PARTY_EVENTS.md. It is not automatically combined with these daily imports and does not change their semantics or optimizer population. Earlier event-ingestion exclusions in this document refer to this aggregate feature, not to that separate ledger.
